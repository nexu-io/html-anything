# Motion release controls on the legacy default branch

This branch retains the legacy HTML Anything application. The Motion application still lives at the root of `feature/motion`. Registration PR #222 is merged into `main`. The follow-up controls below must be merged together with their matching Motion source changes before using the DEV candidate route. These additions do not replace the application, change package/workspace metadata, merge Motion into main, or publish anything on a push/merge.

## Scope and provenance

The three manual workflows, their runtime helpers, installation/acceptance templates and deterministic tests were initially copied without modification from reviewed PR [#214](https://github.com/nexu-io/html-anything/pull/214), source commit `de45dadea282214762c7b3123cea7e6b1044f26f`. The test-channel follow-up copies the same 18 shared control files byte-for-byte from Motion commit `94d15d656eb085f98067867502418bb99c7de0e9` and updates this control set to require DEV candidates and defer npm test promotion until native checks pass. No application business logic or private Git history is imported; shared runtime helpers and tests are included as control dependencies. The extra `Motion release controls` CI job runs only syntax checks and simulated-service tests with read-only permissions; the legacy CI commands and permissions are preserved. Its runner is pinned to Ubuntu 24.04 because the locked Playwright cannot install browsers on the Ubuntu 26.04 image now selected by ubuntu-latest.

The branch-selection/automatic-numbering follow-up copies the same shared control set from Motion commit `b0dd9ddd4af148deda90d42aab0732ba0ab8fe60`. This includes the already integrated #231 shared asset helper and install-guide updates; the candidate gate also runs its native-preparation regression. Empty versions derive from that candidate's frozen Motion source, never from the legacy main package version. Source manifests are not bumped by a build. Both matching PRs must be integrated before accepting feature/motion-produced candidates for publication.

GitHub requires a manual workflow to exist on the default branch before its Run workflow entry is available. All three Motion manual entries now require **Use workflow from: feature/motion**. Selecting `main` fails before checkout or release work instead of silently fetching Motion from another branch. Main still registers the entries for GitHub to display them. The candidate source defaults to the selected dispatch SHA; an explicit reviewed source SHA must be integrated into `feature/motion`. Older valid main-produced candidates remain readable. See [GitHub manual workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

## Activation order

1. PR #214 is integrated into `feature/motion`, and #222 registered the original entries on `main`.
2. Integrate the matching DEV packaging fix into `feature/motion`, then this control-only follow-up into `main`. Recompare the shared control files before using the new route. Neither merge runs a candidate build or publication; normal credential-free CI still runs.
3. An npm package maintainer separately configures the GitHub trusted publisher for `@openmotion/app`: owner `nexu-io`, repository `html-anything`, workflow filename `motion-publish-test.yml`, Environment blank, and both **npm publish** and **Allow npm dist-tag** permissions. The promotion job requires the separate dist-tag permission; publish permission alone is insufficient. Credentialed jobs pin npm 11.21.2, which supports OIDC dist-tag operations. No stored npm token or independent approval environment is required. See [npm trusted publishers](https://docs.npmjs.com/trusted-publishers/).
4. Reuse the existing R2 Secrets `CLOUDFLARE_R2_RELEASES_AK` and `CLOUDFLARE_R2_RELEASES_SK`, and Variables `CLOUDFLARE_R2_RELEASES_BUCKET`, `CLOUDFLARE_R2_RELEASES_URL` and `CLOUDFLARE_R2_RELEASES_PUBLIC_ORIGIN`. Do not add secret values to source. Only the final storage step receives R2 credentials.

These are separate actions. Preparing or merging the registration does not authorize a package publication, repository rename or product-main cutover.

## Daily operation

1. **Build:** Actions → Motion candidate build → Run workflow → select `feature/motion`. Leave version empty to generate the next Motion source patch plus short `-test.N`, e.g. `0.6.4-test.7` from source `0.6.3`. The candidate workflow run number plus 5 continues after historical `test.6`; run #2 gives `test.7`, run #3 gives `test.8`, and a rerun adds `.2`, `.3`, etc. Failed builds and manual overrides consume numbers, so gaps are normal. Keep the workflow file/counter and offset stable; full run IDs remain in candidate records. An an explicit new test-version override remains available. Output metadata is stamped without changing source manifests. Read the resolved version from the successful summary; normally leave `source_sha` empty to freeze the selected `feature/motion` dispatch commit, including while queued. A supplied full SHA must already be integrated into that branch. The build checks/scans source and archives, and retains the exact candidate for 30 days without npm OIDC or R2 credentials.
2. **Download and accept:** Download `motion-candidate-<version>` from the successful run, extract it and give its directory to the Agent: “Follow candidate-install.md, verify candidate.json and the local tgz hash, install the exact local package with an isolated host profile, application home, data and Skills directories, complete prepare, and record actual results in a private copy of acceptance.md. Mark unrun checks NOT RUN. Do not publish.” Keep actual host loading, template/edit/export checks, real Agent creation and human playback separate. New public test software defaults to DEV templates; existing prod test versions retain their original defaults. The package exposes DEV routing configuration without private catalog snapshots or credentials. DEV network access/authentication is still required.
3. **Publish:** Only after acceptance, Actions → Motion test publication → Run workflow → select `feature/motion`. Enter the exact accepted version from the build summary and confirm `accepted`; publication never generates or renames a version. If only a long-numbered candidate exists, build and accept a new short version first; typing a different publication version cannot rename it. This is the publication authorization, with no later independent approval dialog. Candidate provenance/hashes and scans are checked again; only the accepted tgz is published under npm `candidate`, then anonymously checked on Mac/Windows. A separate npm-OIDC-only job verifies both reports, their exact identity and installed DEV defaults, advances `test`, and reads the tag back. Only then does the credential-isolated R2 job archive snapshots and advance the default guide.

Before npm publication, use the candidate's **local** `candidate-install.md`, not the sibling registry `install.md`. After publication, the moving test guide is `https://releases.open-design.ai/open-motion/dev/install.md`; the immutable guide is `/open-motion/dev/<version>/install.md`. Stable publication, npm `latest` promotion and Skills platform/marketplace upload are not implemented by these controls. Five Skills are bundled and installed locally; that is not platform publication.

## Risk and recovery boundaries

- Registration is a capability change: users who can dispatch the trusted publication workflow can confirm and start a public release. There is no independent approval gate at this stage. Protect workflow edits and restrict operational access; the operator confirmation records intent, not proof of private testing.
- Candidate workflows and control changes on `feature/motion` and the registration on `main` require review. The producer branch/SHA is recorded and verified against GitHub run metadata; an arbitrary branch is rejected. Builds do not publish. The publication form defaults acceptance to false and rejects missing, expired, ambiguous or untrusted candidates, changed bytes and unintegrated source. Do not rebuild a published version or guess among duplicate candidate artifacts.
- npm publication cannot be rolled back atomically with later checks. The exact candidate and `candidate` tag are public before native verification. If either native check fails, `test` and the default guide remain unchanged. R2 failure after successful native/tag checks may leave `test` on the verified new version and the default guide on the prior one; this is not an atomic npm/R2 transaction. Inspect `test-promotion.json` and retained attempt records. Never use npm dist-tag as a dry-run against the real registry. Inspect retained records before using Re-run failed jobs; those retries reuse successful producer artifact IDs and never rebuild the candidate.
- Motion snapshot recovery also selects `feature/motion` and writes versioned R2 snapshots for an already published identical npm package; it does not build, publish npm, move tags or access the default guide. Channel rollback and client/data recovery require separate decisions.
- A single publication concurrency group and version/ETag checks protect channel promotion. Operate one release at a time; GitHub does not provide a durable FIFO queue.
- Disabling/removing these workflow registrations later does not undo a published npm version, restore user projects or revoke npm trust. Those are separate operations.

The current [implementation manual](https://github.com/nexu-io/html-anything/blob/feature/motion/docs/release-workflows.md) is maintained with the Motion source; the original #214 snapshot above records registration provenance. For later control fixes, submit paired Motion/main PRs and compare all shared workflow/helper/template/test bytes before release. The maintainer of the control change owns both updates; a main-only registration fix does not update the executable feature/motion controls. Record both PRs and exact commits in the release review. Keep the full acceptance record internal. Real hosted workflow dispatch, npm OIDC, registry-native acceptance and R2/CDN writes need a separately authorized rehearsal; passing these control tests does not establish that those external integrations are active.
