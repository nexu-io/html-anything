# Native Hyperframes authoring · phase one

Read the pinned engine guide returned as `authoringGuide` by project details, or MCP resource `motion://engine/SKILL.md`. Relative engine Markdown references are available below `motion://engine/`. Skills are guidance; the host Agent writes the actual native video.

## Project loop

1. New work uses `motion_create_project` with a stable requestId, projectType, title and requirements. A prompt/reference creates a carrier, not a finished film. Template creation requires a real copyable builtin ID; select it through the Studio gallery or a provided guide. Existing work reuses its projectId.
2. `motion_get_project({projectId})` reads the explicit project, entry HTML, directory, file inventory, requirements, revision and current version. Without projectId it lists five projects per page; follow nextCursor. Never infer another chat's active project.
3. Read text through `motion_get_project({projectId,file:{path,offset,length},expectedRevision})`. Offsets are UTF-8 byte boundaries; follow nextOffset. Media bytes stay out of MCP text responses.
4. `motion_import_assets({projectId,requestId,items:[{itemId,sourcePath}]})` imports real local image/video/audio attachments in a batch. Source paths must exist on the server machine. Check every result and use the returned asset path. Import does not place media on the timeline. Keep stable itemIds for retries; never overwrite historical resources. Successful imports can create a new content version: reread project details before saving with expectedRevision/expectedVersionId. This Tool does not accept fonts, SVG/PDF, arbitrary binary files or remote URLs. Keep such files in an independent portable project using host capabilities; do not bypass managed-project guards by writing binary files directly. Inline SVG markup can be authored in native HTML.
5. `motion_edit_project({projectId,requestId,expectedRevision,expectedVersionId,files:[{path,content}]})` saves one batch of text files and optional requirements. Maximum 100 files / 8 MiB; metadata paths are reserved. All-or-none failure protection uses Studio's exclusive native history window and a recovery journal. Reread after a conflict; do not replay an old patch against unknown GUI changes.
6. For original creation, reference-video recreation and editable-template production, complete the editable preview handoff below once this turn's HTML output is ready. Existing-project content edits follow its continuing-edit rules before writing and after saving, regardless of the selected Skill. Other scopes open Studio on request.
7. Inspect actual motion, timing, sound and affected joins. Local/Studio changes become native content snapshots; querying flushes saved history metadata without editing source. Return to step 2 after GUI edits.

## Editable preview handoff

The first output of original creation, reference-video recreation and editable-template production automatically includes an editable preview. Once the requested HTML and its supporting files/assets have been saved, call `motion_open_preview({projectId})` for that same project, then visibly open its exact returned `previewUrl` in the host's built-in browser. No additional user request or confirmation is needed. This includes drafts and unchanged template HTML; it does not wait for MP4 export. An empty carrier's `index.html` is not the requested output. Explicit user instructions to stay in the background take precedence.

The Tool runs lint and selects an existing project in Studio; it does not create a project or open the host browser. Preserve the URL's embed/query/hash, verify that the intended project and current content loaded, and reuse its browser tab on continued work. If lint fails, fix the reported source problem before retrying. If preview or browser capability is unavailable, provide the project URL when available and state the concrete gap; report the page as opened only after observing it. For an independent folder/ZIP, use a supported managed-project handoff if available; the public MCP has no general folder/ZIP adoption Tool. Preserve the actual source and report that limitation rather than opening an unrelated carrier.

### Continuing edits

For follow-up turns that change an existing editable project's content, confirm the intended project is visible in the host browser before the first write, including scoped edits handled by motion-production. Reuse its existing tab. If the tab is closed, unavailable or showing a different project, call `motion_open_preview({projectId})` for the same project and open the returned exact `previewUrl` in the host browser, then check the project identity. Closing a tab alone does not request background work or cancel an edit. An explicit request to keep working in the background skips opening/focusing the editor and remains in force until the user changes it. Discussion, queries, review-only and export-only turns do not trigger this editing rule.

After the turn's content batch is saved, confirm that the same visible preview shows the requested latest change, using the affected time/frame and sound when relevant. Existing pages normally update from file-change events; reuse that page rather than reopening on every save. `previewSync=file_watcher_notified` and a successful save are not proof of visible freshness. If the page was closed during the edit, reopen the same project before this check unless background work was requested. If it stays stale, reload that existing tab once and check again; report any remaining refresh, loading or browser limitation instead of claiming the latest result is visible. With explicit background work, verify persisted source/version and report visual freshness as unverified.

## Native composition contract

- Root: `data-composition-id`, `data-start="0"`, `data-duration`, `data-width`, `data-height`, and optional `data-fps`.
- Scene hosts: unique `id`, matching `data-composition-id`, `data-composition-src="compositions/scene.html"`, `data-start`, `data-duration`, and `data-track-index`. Scene files wrap markup, styles and scripts inside `<template>`.
- Clips use native timing in seconds. A scene's clock starts at zero. Media trim is `data-media-start`; track index controls the Studio lane, while CSS controls paint order.
- Use the local `assets/gsap.min.js` installed with the default project. Register a paused GSAP timeline under `window.__timelines[compositionId]`. Prefer `fromTo` for repeatable seeking. Do not use wall-clock timers or call `.play()` to drive render animation.
- Use `<video muted playsinline>` for silent footage, or `data-has-audio="true"` to retain sound. Use timed `<audio>` with `data-volume` for separate music or voiceover. Hyperframes handles mixing.
- Keep root duration long enough for all scenes, animations and media. Choose dimensions/fps for the user's deliverable; the old fixed 540×960/24fps limits do not apply.

Only when the selected scope is video recreation, inspect the supplied reference and express its agreed pacing/structure using native clips and source trims; import reference media locally when needed for analysis or authorized final use. A style-only reference in original creation does not require copying its pacing or importing it into the finished project. Implement editable motion as native compositions and use upstream catalog blocks where suitable. Do not promise semantic or pixel-perfect reconstruction without comparison evidence. The old heuristic cut detector and shot-form UI are no longer the active workflow.

For read-only source diagnostics such as lint/timeline/info, or upstream capabilities beyond the installed MCP tools, use host shell capabilities to run `node <hyperframesCli> <command> ...` in the returned project directory using an argument-safe shell invocation. Use official `docs`, `catalog`, `add`, `snapshot`, `check` and other native commands according to their help and the bundled guide. Author/save managed source through the public edit/import Tools; do not use CLI writes to bypass version guards. CLI writes on an independent project affect that directory only. Do not install global skills or replace the pinned runtime as an incidental step.

## Versions and export

`motion_list_versions({projectId})` returns five content versions per page, not five individual-file saves. A version includes source, styles, timing/effects and local resources. `motion_restore_version` requires target versionId and the current expectedRevision/expectedVersionId. Restoring v3 at v5 creates v6; v4/v5 remain. Missing historical resources cause an explicit error before source changes.

Only when the scope includes export/final delivery, use `motion_export_request({projectId,requestId,versionId,expectedRevision,audio})`. Use the currentVersionId from project details as versionId. The service freezes local files/media, lints, renders MP4 and verifies the real file with FFmpeg/ffprobe. Poll `motion_get_project({projectId,exportJobId:jobId})`; only completed with a passed verification is technical success. External URLs remain external dependencies. A later edit cannot change the frozen snapshot.

`motion_export_cancel({projectId,requestId,jobId})` returns cancelling until the owned process exits; cancelled is terminal. Completed jobs stay completed. Stopping a host conversation does not automatically cancel a background job.

Follow [verification](verification.md) for final frames, audio and actual play/seek/replay. Real review evidence can be recorded with action=record_review on preview/export tools; never invent evidence or treat declared user feedback as verified adoption. Keep documents/evidence outside the live project. Preserve native files, media and Studio manifests for editable handoff.
